# Agent Guidelines

## Meta Rules
- **Always update this AGENT.md file when discovering new patterns, rules, or conventions**
- **Always update the Postman collection file when adding or modifying API endpoints**
  - Location: `postman/collections/30029325-1c89067e-99af-49c8-aa89-dd466241d679.json`
  - Include proper folder structure, request bodies, and authorization headers
  - Add test scripts to auto-save tokens for auth endpoints

## Commands
- Build (whole workspace): `cargo build --workspace`
- Test all: `cargo test --workspace`
- Test single: `cargo test test_name`
- Check/lint: `cargo check --workspace`
- Run server: `cargo run -p campus-pilot`
- SQLx prepare (after query changes, from `apis/`): `DATABASE_URL=postgresql://127.0.0.1:5432/campus_pilot cargo sqlx prepare --workspace`
  - **IMPORTANT**: Always run this command (with `--workspace`, so every module crate's queries get checked) after adding or modifying `query!` or `query_as!` macros anywhere in the workspace
  - Commit the `.sqlx/` directory to version control

## Architecture
- Cargo workspace, one crate per ERP module, rooted at `apis/Cargo.toml`:
  - `crates/common` (package `cp-common`) — shared types with zero business logic: `ApiResponse`/`PaginationMeta`, `TenantId`, `Roles`, the `RequirePermission` middleware, `flatten_validation_errors`. Depends on nothing else in the workspace.
  - `crates/platform/audit` (package `cp-audit`) — shared request/correlation context, authenticated actor identity, append-only audit event types, and a transaction-compatible audit writer. Module crates may depend on it without depending on `app`; metadata passed to it must already be reduced and redacted by the owning domain.
  - `crates/platform/imports` (package `cp-imports`) — destination-neutral, bounded CSV/XLSX source parsing and fingerprinting. Destination modules own canonical mapping, deduplication, preview, and commit rules. Retained person-data sources stay private; never place them in the current publicly readable object bucket.
  - `crates/platform/ai-providers` (package `cp-ai-providers`) — tenant-scoped provider catalogue, app-managed write-only credentials, provider connection lifecycle, bounded server-side connection tests, and immutable model snapshots. Credential wrapping uses a deployment-supplied AES-256-GCM keyring with versioned tenant/connection/provider/auth/credential-version AAD. Provider bodies, plaintext credentials, ciphertext, nonces, and wrapping-key identifiers never cross the domain response or Agent boundary. Routing, runs, and usage remain separate concerns.
  - `crates/platform/agent-runtime` (package `cp-agent-runtime`) — tenant-scoped provider routing and private durable Agent Session/run persistence. Only this crate and the dedicated Agent worker may write Agent runtime tables. Every worker mutation must include tenant, run, worker identity, random lease token, and expected monotonic fence version predicates; no route, capability adapter, operational module, or provider adapter may write those tables directly.
  - `crates/agent` (package `cp-agent`) — provider-independent Agent capability descriptors, closed schemas, typed handler registry, proof-bearing broker inputs/scopes, fresh authority and record-scope enforcement, fail-closed actor-aware audit, and the diagnostic module coverage registry. Coverage joins module delivery stage, licensing boundary, workspace route, product operations, Agent classifications, and registered handlers; it never grants access. The executable registry is indexed against `cp-common` product operations and initially accepts only directly exposed read/export handlers; operational modules never depend on `cp-agent`.
  - `crates/app` (package `campus-pilot`, binary + lib) — the platform layer: kernel bootstrap, auth, users, roles, access/licensing, storage, `AuthMiddleware`, `AppState`, `main.rs`. Depends on `cp-common` and every module crate (it's the only crate that mounts everything into one `actix_web::App`).
  - Production Agent adapters for app-owned Administration services live in `crates/app/src/services/agent/`; they call the same typed service or pure catalogue source as HTTP routes and are assembled once into `AppState.agent_capabilities`. Shared read projections such as licensing state live beside their domain service and are consumed by both HTTP and Agent entry points. Never duplicate route logic or make private HTTP calls from a capability.
  - `crates/modules/<name>` (packages `cp-<name>`) — one ERP module each (`fleet`, `vehicle-log`, `sis`, `academics`, `gradebook`, `academic-reporting`, `attendance`, `activities`, `learning`, `student-support`, `transport`, `facilities`, `finance`, `fees`, `hr-payroll`, `procurement`, `assets-inventory`, `library`, `messaging`, `hostel`, `health`). Each follows the same `mod.rs`/`models.rs`/`dtos.rs`/`ops.rs`/`routes.rs` split as `app`'s own services. **Module crates never depend on `app`** — this is what lets `app` depend on all of them without a cycle. A module crate MAY depend on a sibling module crate when there's a genuine domain relationship (for example, `cp-gradebook` depends on `cp-academics` and `cp-sis` for canonical component and roster reads). Cross-module reads go through typed owning-module operations rather than copying another module's SQL joins.
- HR and payroll owns the canonical `Employee`, dated employment engagements, and reviewed availability periods. The active engagement is the source for the employee directory's current department, position, dates, and status projection. A system `User` account is an optional one-to-one authentication link, never an automatically created employee side effect. Role-specific records such as Fleet drivers and Academic teachers are module-owned profiles keyed to the employee and must not duplicate employee identity or contact fields. Employee imports deduplicate by employee number and normalized work email, resolve department and position through HR-owned references, and never create login accounts.
- Shared CSV/XLSX imports are staged workflows: retain the source and mapping version, validate and deduplicate without mutation, present an immutable preview, require explicit commit authority, and retain row-level results. Each destination module owns its canonical fields and commit operation; imports never create login accounts implicitly.
- Academics owns academic years, non-overlapping academic terms, canonical tenant-wide grade levels, subjects, classes, employee-backed teacher profiles, teaching assignments, and term-scoped assessment structures. Classes reference a canonical grade-level identifier rather than storing a copied label. Assessment cycles move forward from draft to open to closed. Components reference canonical teaching assignments, resolve class/subject/teacher rather than copying them, and must total exactly 10,000 basis points per assignment before the cycle opens. CSV/XLSX imports must resolve external grade codes or labels through their saved mapping before preview commit; an unresolved grade blocks that row. Terms remain inside their academic year and move forward through planned, active, and closed states. Timetabling requires the active term, consumes Academics records through typed `cp-academics` operations, and consumes only the minimum approved HR availability fields needed for that term. Dated HR availability is a planning constraint, never a permanent weekly slot. Timetabling owns recurring schedule rules, rooms, room preferences, immutable generated snapshots, and publication state. SIS remains the source of learner enrolment and class placement; learner mark capture must validate SIS enrolment through a typed boundary rather than duplicating learners in Academics.
- Attendance owns dated class registers, timetable-linked lesson sessions, per-learner marks, learner history, and the current exception follow-up state derived from immutable submission evidence. Daily register operations require Academics and SIS entitlements; lesson-session operations additionally require Timetabling and materialise only the current published timetable. It obtains active terms, classes, subjects, and exact current teacher assignments through typed Academics operations and date-effective roster membership and display identity through typed SIS operations. Teachers have assigned scope and may prepare, edit, and submit only registers and lesson sessions for their own active teaching assignments; Attendance Officers have campus scope and alone may sync or cancel lesson sessions, manage exceptions, reopen submitted registers, and delete drafts. It stores stable enrolment, learner, assignment, and timetable identifiers rather than copied identity. Registers are optimistic-versioned drafts until every learner is marked and submitted; each submission appends an immutable full-roster snapshot and creates or reconciles the operational exception queue without claiming that any notification was sent. Lesson-session and exception lifecycle evidence is append-only, submitted marks remain immutable until a reasoned manager reopen, and writes append `cp-audit` in the same transaction.
- Learning owns class-linked spaces, ordered units, governed resource references, published assignments and rubrics, versioned learner submissions, released feedback, and derived progress. It requires Academics, SIS, HR and payroll, and Document Registry entitlements. Teachers author only within assigned teaching spaces; Students use `learning:participate` only for their own current-enrolment submission; Academic Managers use campus scope. Publishing an assignment freezes its content, rubric, and exact SIS roster. Learner drafts are mutable and optimistic-versioned, but every submit or resubmit appends an immutable text snapshot under an idempotency key. Feedback targets an immutable submission version; released grades and revision requests are immutable. Progress is derived rather than separately stored. Learning never creates a learner, employee, login, mark ledger, or second file store; formal marks remain Academics-owned, governed resources remain Document Registry-owned, and learner file submissions require a later explicit retention contract. Successful writes append reduced Learning lifecycle evidence plus `cp-audit` in the same transaction and never place submission or feedback text in audit metadata.
- Document Registry requires `document_registry:restricted` for restricted metadata, derived counts, mutations, disposition work, and human downloads. Every mutation must authorize the current stored sensitivity inside its locked write predicate; checking only a requested replacement sensitivity is insufficient. Closed file metadata and classification evidence is immutable, and disposition request creation and decision lock and recheck the file and review in the same transaction. Terminal files, reviews, released legal holds, and completed deletion jobs reject mutation at the database boundary. An active legal hold blocks destruction approval, queueing, and worker claims; hold creation locks the file and rejects once deletion is processing. Approved destruction becomes `deletion_pending`, then a leased, retryable worker deletes the private object before atomically recording the file, review, job, activity, and audit terminal states. Authorized private downloads append reduced activity and `cp-audit` evidence without object keys or signed URLs. Wildcard permission never substitutes for the required `document_registry.records=campus` scope.
- Activities owns the catalog, dated groups, employee-backed leaders, learner memberships and consent, scheduled sessions, participation, immutable completion snapshots, and append-only lifecycle evidence. It requires SIS and HR and payroll entitlements and resolves people only through typed owning-module operations. Activities Coordinators have campus manage/operate access; Activity Leaders operate only groups assigned through their active employee record; Students read only their date-effective membership and participation; Teachers receive no seeded Activities permission. Mixed Student and Activity Leader roles never extend session writes from assigned scope into self scope. Existing records use optimistic versions, completion evidence is immutable, and writes append lifecycle plus `cp-audit` evidence in the same transaction.
- Transport owns school routes, ordered stops, dated learner rider assignments, service runs, immutable run snapshots, manifests, and append-only run events. It requires Fleet and SIS entitlements, resolves current learner identity through typed SIS operations, and accepts only active Fleet vehicles and employee-backed drivers through typed Fleet operations. It never creates shadow learners, users, employees, drivers, or vehicles. Transport Officers receive campus `transport:view` and `transport:operate`; Transport Managers additionally receive `transport:configure` and `transport:manage`. Route and stop configuration remains administrative, while run operation covers boarding, manifest marking, departure, and completion. A complete manifest is required before departure; cancellation is manager-only and reasoned. All writes use optimistic versions where an existing record changes and append reduced `cp-audit` evidence in the same transaction.
- Facilities owns typed campus locations, service requests, work orders, immutable completion submissions and inspections, and append-only lifecycle evidence. It requires HR and payroll, references active employees for assignees, and never creates shadow people or login accounts. Teachers and Staff Members receive `facilities:view` and `facilities:request` with self request scope only. Facilities Officers receive assigned work-order scope and `facilities:operate`; Facilities Managers receive campus scope and `facilities:manage`. Only managers configure locations, assign or cancel work, inspect completion, and close requests. Every mutable-record write uses an expected optimistic version, lifecycle evidence and audit are appended in the same transaction, and completion/inspection/event rows reject updates and deletes at the database boundary.
- Student Support owns learner-linked restricted cases, active case teams, append-only case actions, and append-only lifecycle evidence. SIS owns learner identity; Student Support stores only stable learner and user identifiers and resolves current display fields through typed SIS and core-account operations. A case always has one non-null lead. Case Workers have assigned scope and may create only with themselves as lead; Student Support Managers have campus scope and alone may change teams or escalate, resolve, and close cases. No Teacher, School Administrator, Registrar, Student, or Guardian permission is seeded. Every write re-proves exact current scope inside its transaction, uses optimistic versions, and appends reduced `cp-audit` plus module lifecycle evidence before commit. There is no hard-delete route.
- Gradebook owns assessment mark sheets and exact learner marks while remaining an Academics product workspace. It requires Academics, SIS, and HR and payroll entitlements, obtains component identity through `cp-academics`, and obtains date-effective roster membership through `cp-sis`. Marks use integer hundredths; mark sheets move draft to submitted to published, use optimistic versions, require complete rosters before submission, and retain a reason for every reopen. Assessment cycles cannot close until every active component has a published sheet. Lifecycle evidence is append-only and writes `cp-audit` in the same transaction.
- Academic reporting owns versioned grading schemes, immutable calculated subject and attendance snapshots, report-card remarks, progression decisions, publication, and published learner transcripts while remaining an Academics workspace. It requires licensed Academics, Gradebook, Attendance, SIS, and HR and payroll records. It consumes only typed published Gradebook evidence, submitted Attendance summaries, and date-effective SIS rosters; it never edits those sources or duplicates their mutable queries. Draft report batches move to reviewed and published, retain a source fingerprint and grading-scheme snapshot, require optimistic versions, and reopen only with a recorded reason. Student and guardian self access sees published cards only; teachers see assigned classes; academic managers see campus records.
- SIS owns canonical learner and guardian records, explicit many-to-many guardian relationships, applications, and enrolments. Learner and guardian login accounts are optional one-to-one links; SIS never creates credentials as a person-record side effect. Applications reference an Academics-owned year and canonical target grade; enrolments assign an Academics-owned class in that year and must match the source application's target grade. SIS never copies those records.
- Finance owns the campus currency register, chart of accounts, fiscal years, accounting periods, and journal ledger. Exactly one active currency is the reporting currency. Accounts explicitly use the reporting currency, one selected active currency, or multiple transaction currencies; do not infer currency from symbols or locale. Summary accounts may contain same-type child accounts and cannot accept postings; posting accounts cannot become parents. Fiscal-year date ranges cannot overlap; generated periods cover the full year without gaps. Only draft years can be renamed or removed, period status changes require an open year, and a fiscal year closes only after every period closes. Closed years are not reopened. Journals store integer transaction and reporting minor amounts, currency and account snapshots, idempotency keys, and typed source-record references. Drafts must balance before submission; a preparer cannot approve or post their own entry; posting is immutable; corrections create a separately reviewed reversal draft. Other modules submit balanced, idempotent posting requests and never write Finance ledger rows directly. Import previews may propose journal drafts but never post implicitly. Payment-provider credentials and provider-specific references belong to a provider adapter boundary, not currency, account, or accounting-calendar tables.
- Treat every module persona as a profile over one canonical identity: Driver and Teacher reference Employee; Student access references Learner; Guardian access references Guardian. Authentication roles grant access but never create or replace those domain records.
  - Module route handlers take `web::Data<sqlx::PgPool>` (registered as its own `app_data` in `main.rs`, alongside the full `AppState`) and `web::ReqData<TenantId>` — never `AppState` directly, so they stay decoupled from `app`.
- Auth vs. permissions split, mount order matters: `AuthMiddleware` (verifies the JWT, loads the `User` row, resolves effective role permissions and enabled modules, and inserts `User`/`TenantId`/`Roles`/`AccessContext` into request extensions) lives only in `app` and is applied at the OUTER scope when a module is mounted (see `crates/app/src/routes.rs`). `RequirePermission::new("<module>")` lives in `cp-common` and resolves the matched method and route pattern through the exact product-operation catalogue before evaluating module state, dependencies, permission, and future runtime checks. Only an explicitly uncatalogued compatibility route may fall back to HTTP-method inference (GET→view, POST→create, PUT/PATCH→edit, DELETE→delete), and missing descriptors are logged as errors; every released protected route must be catalogued. **When a scope needs both**, `AuthMiddleware` must be the LAST `.wrap()` call (outermost, runs first) so `RequirePermission` sees populated access context; e.g. `.wrap(RequirePermission::new("users")).wrap(AuthMiddleware)`.
- Agent message submission treats `origin_module_key` and `origin_route` as untrusted. The app route must refine them through the code-owned client route map and the request's current `AccessContext` before constructing a runtime command; unknown or mismatched paths, missing entitlements, locally unavailable modules, and missing exact route permissions fail before Session/run persistence.
- A capability rejected during broker preparation is a terminal non-executable intent, not an `agent_capability_call`. The worker must record it through `AgentSessionOps::record_capability_rejection` before returning a tool error. That fenced function validates the exact current worker, raw lease token, queue fence, checkpoint, run actor, request, and correlation under row locks; the raw token is never retained, and unavailable operation, input, or scope evidence stays `NULL`.
- Role assignments store immutable `roles.key` values, never editable display names. Seeded system roles may be renamed, but their permission baselines are fixed and they cannot be deleted; use dynamic custom roles for different or combined responsibilities. Custom roles cannot be deleted while assigned. The seeded Teacher remains an assigned-class practitioner: it never receives user/role administration or Academics create/edit/delete/manage permissions; teachers record assigned marks through `academics:teach` instead of configuring teacher profiles, grade levels, grading policy, publication, or progression.
- A wildcard permission (`*`) grants every action only inside modules currently enabled for the tenant. It never bypasses module licensing.
- A wildcard permission never creates record scope. Campus Owner remains an administrative authority until an explicit operational role contributes the required self, assigned, or campus scope. Clients must filter launcher modules and direct routes with the authenticated `record_scopes` projection and must not treat `*` as campus visibility.
- The canonical module and permission catalogue lives in `crates/app/src/services/access/catalog.rs`. Validate role permissions against this catalogue; do not add free-form permission strings in UI code or feature modules.
- Signed license activation stores only a key fingerprint and verified entitlement claims. Never persist, log, or return the original license key.
- **Never nest multiple `web::scope("")` (or any identically-patterned scopes) under the same parent scope** to apply different middleware per HTTP method — actix-web only honors the first such nested scope and silently 404s the routes registered in the others. This was a real, previously-shipped bug in `users`/`roles`; the fix was the single `RequirePermission` wrap described above.
- Entry point: `crates/app/src/main.rs` (binary), `crates/app/src/lib.rs` (library)
  - Structure per service/module: `models.rs` (data types), `dtos.rs` (request/response types), `ops.rs` (business logic / queries), `routes.rs` (actix handlers + `routes(cfg)`)
  - Hostel learner identity stays SIS-owned. Allocation and transfer writes are two-step decisions: preview capacity and dates, then submit the server fingerprint while the transaction locks and revalidates room/version/overlap evidence. Never accept a client-computed availability value or overwrite completed allocation history. Pastoral records use a separate sensitive campus-only scope even when occupancy access permits self reads.
  - Health record visibility is deliberately either `self` or `campus`; there is no assigned-patient interpretation. Resolved care items, ended medication plans, and completed or cancelled follow-ups are terminal evidence and must not be reopened or rewritten. Medication administration must lock and re-check the active plan in the same transaction so a concurrent suspension or ending cannot accept a dose afterward.
- Database: PostgreSQL with SQLX migrations in `migrations/` (still centralized, not per-crate); reserved numbering: 001-003 core, 004-009 tenancy, 010-011 fleet/vehicle-log, 020s SIS, 030s academics, 040s finance, 050s fees, 060s HR/payroll, 070s procurement, 080s library, 090s messaging, 100s hostel, 110s health (see `ROADMAP.md`)
- Migration versions are append-only once applied. If the database has already applied a higher version, use the next unused version for a follow-up even when the change belongs to a module whose original reserved range is lower; never insert an out-of-order migration beneath an applied version.
- Multi-tenancy: every ERP table carries `tenant_id`; a single-tenant on-prem install is just a deployment that only ever provisions one tenant (seeded by migration 004, used by kernel bootstrap) — same schema and code path as multi-tenant SaaS, no special-cased mode
- Testing: Integration tests in `crates/app/src/tests/`, unit tests use `#[actix_web::test]`. Each test runtime creates its own SQLx pool; `tests/helpers.rs` serializes idempotent migration passes with a PostgreSQL advisory lock so a fresh migration is safe under the default parallel test runner. Known baseline issues remain: setup and user tests reuse fixed bootstrap/user records in the same database across runs, and the activate/deactivate user tests still call stale HTTP methods.

## Code Style
- File headers: Include copyright header with creation date and author
- Imports: Group std, external crates, then local modules
- Error handling: Use `anyhow::Result` for main functions, custom errors for API responses
- Types: Use `serde` for JSON serialization, `sqlx` types for database
- Naming: snake_case for variables/functions, PascalCase for types/structs
- API responses: Wrap in `ApiResponse<T>` struct for consistency
- Routes: Use attribute macros (`#[get]`, `#[post]`, `#[put]`, `#[delete]`) on handler functions
- Middleware: Apply at scope level, not individual routes (e.g., `.wrap(AuthMiddleware)`)
- Authentication: All protected routes must use `AuthMiddleware` and appropriate `RequirePermission` middleware

## SQL Style (PostgreSQL)
- All SQL keywords should use UPPERCASE (CREATE, SELECT, INSERT, UPDATE, DELETE, etc.)
- All PostgreSQL data types should be UPPERCASE (TEXT, INTEGER, BOOLEAN, UUID, etc.)
- All built-in functions should be UPPERCASE (NOW(), LOWER(), TO_JSONB(), etc.)
- All control flow keywords should be UPPERCASE (BEGIN, END, IF, THEN, ELSE, etc.)
- All trigger/function keywords should be UPPERCASE (RETURNS, LANGUAGE, EXECUTE, etc.)
- Column names and table names should remain lowercase with underscores
- String literals and comments can remain as-is
- All create statements should include IF NOT EXISTS
- All tables should have deleted_at, created_at, and updated_at fields
